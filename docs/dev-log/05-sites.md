# ⑤ 外部サイト（メール・スプレッドシート・専用サイト・インフォマート／発注の送り出し）— 作業記録

担当: 受注の取り込み（メール・Google スプレッドシート・得意先の専用サイトの CSV・インフォマートの CSV）と、発注の送り出し（承認 → FAX用PDF・メール下書き・サイトの入力用リスト）
期間: 2026-11-04（ハッカソン期間中に新しく作成）
社名・品名・数量はすべて架空。

---

## 1. 何を作ったか（流れ）

```
【受注】
 メール(.eml：本文・PDF添付・Excel添付) ─Claude が読む─┐
 Google スプレッドシート（店舗別・月別） ─前回との差分─┤
 得意先の専用サイトの CSV（23列・Shift_JIS）─振り分け─┤→ 共通の Order（要確認）→ 人が確定 → 集計・製造計画・発注（②③）
 インフォマートの受注 CSV ─見出しで列を探す──────┘

【発注】
 ③の発注書の下書き → 人が「承認」→ 送り先ごとの出力を作る（送らない）
   FAX: 発注書PDF → 「FAX 送信待ち」一覧 → 人が複合機から送る → 「送った」
   メール: PDF を添付した下書き（.eml）→ 人がメールソフトで送る → 「送った」
   サイト: 画面と同じ並びの入力用リスト（＋取り込める CSV）→ 人が入力して確定 → 「送った」
```

| 順番 | やったこと |
|---|---|
| 1 | 業務の全体像のメモと、取引先の専用サイトの本物の CSV・振り分けの Excel を**読むだけ**で調べ、列の並び・数量の持ち方・振り分け先の分け方をつかんだ（中身はリポジトリに入れていない） |
| 2 | 共通の部品 `src/lib/channels/common.ts`：取り込んだものを「要確認」の Order にする。同じ ID は読み直しで置き換えるが、**人が確定・取消した注文は上書きしない** |
| 3 | 架空のサンプルを作るスクリプト `scripts/make-inbound-samples.ts`：PDF の発注書、Excel の注文書、本文の注文・数量変更・キャンセルのメール（.eml）、シートの1回目と書き換え後、専用サイトの CSV（朝・昼）、インフォマートの CSV |
| 4 | メールの取り込み `email/`：.eml を開き、本文・PDF・Excel を Claude に渡して読ませる |
| 5 | 変更・キャンセルのメールは、元の注文を探して `intent` と `changeOf` でつなぎ、**別の注文（要確認）として入れる**。元の注文は書き換えない |
| 6 | スプレッドシート `google_sheet/`：URL＋シート名＋範囲で読み、前回の値と比べてセルごとの差分を出す。確定済みの日に差分が出たら「変更」の注文を別に作る |
| 7 | 専用サイトの CSV（専用サイト用のフォルダ）：事業所ごとの注文、振り分け表（仕入先への本発注・前日分・自社製造・包装・菓子パン）、朝→昼の数量差、札の一覧。発注書は③の通常の計算に一本化（二重計上を避けるため） |
| 8 | インフォマートの CSV `infomart/`：列は見出しの言い方で探す（実物の列名を1か所に足せば読める） |
| 9 | 発注の送り出し `outbound/`：承認 → 発注書PDF・メール下書き・入力用リスト・CSV。状態（下書き・承認・送信済み）は③の `purchase-store` だけに持つ |
| 10 | インフォマートの画面調査（担当者がログイン → Claude は読むだけ）。発注 CSV の取り込みがないと分かり、サイト向けは入力用リストだけにした |
| 11 | こちらから FAX を送る方法の調査と案（`docs/fax-sending.md`）。デモは「承認 → PDF → 送信待ち」まで、送信ボタンはダミー |

## 2. Claude API の使い方

- モデル: `claude-opus-5-5`（adaptive thinking、effort: high）。①の FAX 読み取りと同じ呼び方にそろえた
- 出力: **Structured Outputs**（Zod スキーマ → `betaZodOutputFormat`、`client.beta.messages.parse()`）
- 断られたとき: server-side fallback（`fallbacks: "default"`）、`stop_reason: "refusal"` は「手入力で」と返す

### 入力の渡し方（1通のメールを1回で読む）
- **本文** … テキストのまま
- **PDF 添付** … `document`（base64）でそのまま渡す。文字起こしや画像化はしない
- **Excel 添付** … Claude の入力に Excel は直接入れられないので、`exceljs` でセルを読み、「行番号: セル | セル | …」の表のテキストにして渡す。シート名も付ける
- 件名・差出人・受信日時と、得意先一覧・商品一覧を一緒に渡す

### 指示（システムプロンプト）の工夫
- AI の役割は「書いてあるとおりに読む」「人が確認すべき所に印を付ける」まで。ケース→個の換算はさせず、`quantity` と `pieces_per_unit` を分けて返させる
- メールの種類を `intent`（新規・変更・キャンセル・注文ではない）で返させる。「追加」は前の注文に足すので変更として扱わせる
- 変更は「変更後の数」を `quantity`、書いてあれば「変更前の数」を `previous_quantity` に。変更しない品は入れない
- 本文と添付の両方に同じ注文があれば1回だけ入れ、数が食い違えば両方入れて `attention` に書かせる
- 「明日」「来週月曜」や年のない日付は、受信日から日付に直し、元の書き方を `attention` に残させる
- 変更・キャンセルのときは元の注文番号や元の納品日を `refers_to` で返させ、プログラムが元の注文を探す

### 結果（架空のメール5通）
- PDF の発注書：発注番号・納品先・納品日2日分・ケースの入数（10枚入）を読めた。商品一覧にない試作品は、商品を空にして「登録の確認が必要」と印を付けた
- Excel の注文書：5日分の表（空欄＝注文なし）を日ごとの注文に分けられた。袋の入数（10個入）も拾った
- 本文の数量変更：「300枚 → 360枚」を変更として読み、元の注文とつながった。キャンセルも元の注文とつながった
- 思わぬ収穫：私が作ったサンプルの「11月11日（火）」（実際は水曜）に、Claude が「曜日が合わない、確認を」と印を付けた。人が見落としやすい所を拾ってくれる

## 3. 試行錯誤して直したこと

| 起きたこと | 原因 | 直し方 |
|---|---|---|
| 発注書 PDF の日本語が半分くらい欠ける | 最初に使った PDF ライブラリ（pdf-lib）が、大きな日本語フォントの文字の切り出しでうまく動かなかった | `pdfkit` に替えた。使った文字だけ埋め込むので、1枚20KB前後と軽い |
| サンプルの曜日がずれていた | 2026年11月の曜日を思い込みで書いた | Claude の指摘で気づき、計算して直した |
| 得意先の ID が他の担当とぶつかった | 並行で①も C09 を足していた | マージ後に自分の分を C10〜C13 に付け直した |
| 送り出しの状態を自分で持っていた | 最初は独自の保存ファイル（outbound.json）で「承認・送信済み」を管理していた | ③の `purchase-store`（`approvePurchaseOrder` / `markSent`）に一本化。承認していない発注書は送信済みにできない決まりも③のものを使う |
| 専用サイトの分が二重に発注されそう | 振り分けから発注書を作ると、確定した注文から③が作る発注書と重なる | 振り分けからは発注書を作らず、表と注文の行に「仕入先・便・届く日」だけを書く。発注書は③に一本化 |
| インフォマート向けに発注 CSV を作っていた | 「CSV で一括取り込みできるはず」という思い込み | 画面調査で、そのアカウントには取り込みがないと分かったのでやめ、画面の並び・手順どおりの入力用リストにした |
| 画面や PDF に実在の社名が出る | マスターの仕入先名に「（○○相当）」という注記が入っていた | 画面と発注書では注記を外して表示。振り分け先の名前も架空の名前にした |
| 画面のマージで衝突 | ②が共通部品で見た目をそろえたのと同時に、⑤が処理を変えていた | ②の見た目（共通部品）を残し、⑤の処理を入れ直して解消 |
| 画面からの取り込みテストで、2つのサンプルが同じ結果になった | テスト用のスクリプトで、2つを同時に送ったときに同じ一時ファイルを使っていた | 1つずつ送り直して確認（アプリ側の不具合ではない） |

## 4. Claude Code の機能で使ったもの

| 機能 | どう使ったか |
|---|---|
| **並行セッション（git worktree）＋セッション間のメッセージ** | ⑤は専用の worktree・ブランチで作業。管理役のセッションに、得意先の追加・型の追加（`intent`／`changeOf`、発注方法の追加）を相談し、マージや衝突の連絡を受けた。ログイン画面の準備ができたことも、メッセージで知らせた |
| **MCP（Chrome 拡張）** | インフォマートのログイン画面を開くところまで Claude が行い、ID・パスワードは担当者。ログイン後の画面は、読む操作とタブの切り替えだけ（発注・確定・設定変更・ダウンロードは押していない） |
| **アプリ内ブラウザ** | 自分の開発サーバー（ポート 3104）の `/import`・`/outbound` を開き、取り込み・承認・FAX送信待ちの流れを画面で確かめた |
| **Web 検索** | プリンターの複合機でパソコンから FAX を送る方法（ネットワーク FAX ドライバー・HyPAS）を調べた |
| **Bash／Python（読むだけ）** | 本物の振り分けの Excel（.xls）と CSV の形を、Python で読んで調べた。元のファイルは変更していない |
| 使っていないもの | サブエージェント・フック・AskUserQuestion・Gmail などのメール系 MCP は使っていない。`claude-api` スキルも読み込んでおらず、①がスキルを使って書いた FAX 読み取りの呼び方に合わせた |

## 5. 守ったルール
- AI は読み取りと印付けまで。値を直すのは人。取り込みは必ず「要確認」で入り、人が確定・取消した注文は取り込み直しでも上書きしない
- 変更・キャンセルは新しい注文として入れ、元の注文は人が確定するまで書き換えない
- 元の読み取り値（`read`）を必ず残す
- 発注書は「下書き → 人が承認 → 人が送る → 人が『送った』を押す」。自動で送るしくみは作らない（FAX の送信ボタンもダミー）
- ID・パスワードは Claude が入れない。ログインは担当者。ログイン後の画面は読むだけ
- 複合機の設定は変えていない
- 公開リポジトリなので、取引先・品名・数量・単価はすべて架空。本物の資料は読むだけで、中身はリポジトリに入れていない
