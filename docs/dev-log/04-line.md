# ④ LINE注文 — 作業記録

担当: お客さん（喫茶店・小さな店・介護施設。年配の店主が多い）が LINE からパンを注文できる入口。トークの文章を Claude API で読み取る仕組み、LIFF の注文フォーム、リッチメニュー、確定の連絡、LINE 側の設定の案内
期間: 2026-11-04〜11-05（ハッカソン期間中に新しく作成）
作業したところ: Claude Code のセッション1つ（git の worktree `claude/line-order-*` ブランチ）。進行役のセッションと、①FAX・②画面・③計算・⑤外部サイトの各セッションが並行で動いていた。
LINE 公式アカウント: 本番の公式アカウントを1つ使用（ID は公開リポジトリなので書かない）

## 1. 何を作ったか（流れ）

| 順番 | やったこと |
|---|---|
| 1 | 業務の全体像のメモと、共通の型（`Order`・`SourceRef` の `line_message`）・保存先（`store.ts`）・FAX の取り込み例を読んでから始めた |
| 2 | **LINE なしで試せる仕組みを先に作った**。Webhook と同じ形の架空メッセージを流し込む `scripts/line-webhook-test.mjs`。`.env.local` が空のときは「デモモード」になり、LINE には送らず、送るはずの文面を `data/line.json` に記録する |
| 3 | **Webhook** `src/app/api/line/webhook/route.ts`：署名（`x-line-signature`）を確かめる → すぐ「受け付けました（確認中）。」とだけ返す → 応答のあと（`after()`）で Claude が読み取り、`Order`（channel: line、status: needs_review）を作る |
| 4 | **トークの読み取り** `src/lib/channels/line/reader.ts`：話し言葉・略称（「バタロ」「黒糖のちいさいロール」）、「明日」「金曜」、単位違い（食パンを「本」で）を読む。自信がない行は confidence を下げ、理由を attention に書く |
| 5 | **変更・取消の連絡**：「金曜の分のバタロを25個に」→ intent: change、changeOf に元の注文ID（Claude が最近の注文の一覧から選ぶ）。元の注文は触らない |
| 6 | **初回のひも付け**：LINE の userId とお店は、人が1回だけ選ぶ（`/line`「LINE受付」）。選ぶと、その人の「お店が不明」の要確認注文にも、修正履歴つきでお店が入る |
| 7 | **確定の連絡**：人が確定したあと、ボタンを押したときだけ「ご注文を確定しました」と内容を送る。1件につき1回だけ（`source.extra.lineNotifiedAt`）。変更・取消は文面を変える |
| 8 | **LIFF の注文フォーム**（1作目）：大きな文字と＋−を縦に並べた → 作者から「ダサい」 |
| 9 | ほかの LINE 注文（BtoB 受発注、飲食のモバイルオーダー、LINE ミニアプリの決まり、リッチメニューの作り方）を15件ほど調べ、自社のホームページの色（深い赤・クリーム・金、明朝体）を確かめて**作り直した**（2作目） |
| 10 | **リッチメニュー**：上半分が「パンを注文する」、下に「前回と同じ」「注文の履歴」「使いかた」。画像は HTML で作って Chrome で画像にし、Messaging API で登録（`scripts/line-richmenu.mjs`） |
| 11 | **LINE 側の設定**を作者と一緒に行い、本番の LINE につないだ（公式アカウント作成 → Messaging API → 応答設定 → チャネルの合いかぎを `.env.local` へ → Webhook → LINE ログインのチャネルと LIFF → 公開） |

注文フォームの流れ（2作目）

```
お届け日（横に並んだ日付カード。締め切り後の日はうすく押せない）
  → 前回と同じ内容で（1タップで確認へ）／商品の「＋」→ −数＋（数字を押すとテンキー）
  → 下の固定バー「確認する」→ 下から出る確認シート →「この内容で注文する」
  → 受け付けました（確定したら LINE でお知らせ）
```

## 2. Claude API の使い方（トークの読み取り）

- 場所: `src/lib/channels/line/reader.ts`（サーバー側だけ）。モデルは FAX と同じ Opus。adaptive thinking、effort は medium（文章は短いので FAX より軽く）
- **構造化出力**（zod のスキーマ `LineReadSchema`）で、注文か・納品日ごとの行・意図（new / change / cancel）・対象の注文ID・品名・数・単位・自信度・確認してほしい点を返させる
- **渡すもの**：商品一覧（catalog）、そのお客さんについて人が承認した「品名 → 商品」の対応、そのお客さんの最近の注文8件（変更の対象さがし用）、受信日時（日本時間）
- **AI がやるのは「読む」と「印を付ける」まで**。換算（本 → 斤など）はしない。商品一覧にないもの（例：「カレーパン」）は商品を空にし、「取り扱いを確認」と書く
- 読み取りに失敗しても、原文つきの要確認の注文として必ず残す（人が手で入れる）
- 同じメッセージが2回届いても（LINE の再送）、注文は1つだけ作る

本番で届いた例（作者のスマホから）：「明日カレーパン6個お願いします」→ 納品日は翌日、カレーパンは商品一覧にないので confidence 0.3、「夜11時すぎの受信なので、明日の納品に間に合うかも確認が必要」というメモまで付いた。

## 3. LINE 側の設定で学んだこと

- LINE 公式アカウントは **LINE Official Account Manager で作り、そこで Messaging API を「利用する」**。Developers コンソールで Messaging API のチャネルを直接は作らない
- LIFF は **LINE ログインのチャネルに付ける**（Messaging API のチャネルには付けられない）。同じプロバイダーにしておくと userId がそろう
- LINE ログインのチャネルは **「開発中」のままだと開発者しか LIFF を開けない**。「公開」は元に戻せないので、作者の OK を取ってから押した
- 会社で使うので、ビジネス ID は**個人の LINE ではなく会社のメールアドレス**で作った（スマホを替えても、人が替わっても続けられる）
- 応答メッセージ・あいさつメッセージ・チャットは**オフ**（ハブが返事をするので、二重にしない）
- Webhook の「検証」は、トンネルをつないだ直後の1回目に失敗し、2回目で成功した
- `reply`（返信）の合いかぎ（replyToken）は1回しか使えない。返事は読み取りの前にすぐ返す
- リッチメニューの大きいサイズ（2500×1686）は、ボタンを大きくできて年配向き。PC 版の LINE には出ない
- トンネル（cloudflared）の URL は起動のたびに変わる。撮影日など起動し直したら、Webhook URL と LIFF のエンドポイント URL を貼り直す（`docs/line-setup.md`）
- 外から来るアクセスは、①の `src/proxy.ts` で `/api/line/` と `/liff/` などだけを通す。LIFF の入口は `/liff/order` に置いた

## 3-2. 夜間の作業（11/4 夜〜11/5 朝）

管理役の方針変更（「ひも付けは取引先マスタの画面で」「保存は①の SQLite に」）を受けて作り直した。

- **SQLite 化**：LINE の人とひも付けは masters の `line_users` に入れ、変更は master_history に残る。ひも付け・解除の記録は `line_link_log`、送った文面の記録は `line_outbox` に入れる（どちらも①の SQLite）。前の `data/line.json` は、最初に読んだときに1回だけ取り込み、`line.json.migrated` に名前を変える。テストは `HUB_DB_PATH=":memory:"`
- **ひも付けの画面**：`/admin/customers`（②の AdminPage）の一覧の上に「LINE アカウントのひも付け」を置いた。お店が分からない LINE の人を、名前・最初の文章・日時つきで並べる。取引先を選んでひも付けると、その人の「お店が不明」の要確認注文にもお店が入る（修正の記録つき）。「新しい取引先として登録」と「解除」もできる。`/line` は受付と確定の連絡だけにした
- **取引先マスタ**：masters の `customers` は④が持つ。列の決まりは③の `customerDef` に合わせた（`src/lib/masters/customers.ts`）。初期値は `src/lib/db/seed/customers.ts` に置いた。実際のコース表の傾向（朝5時半〜昼の納品、FAX が最も多い、納品のときに次回分を聞く・電話・インフォマート・LINE）に近づけたが、名前は架空のまま。編集フォームの下で、注文の入口・締め・納品時刻・配送コースを直せる
- **名寄せ辞書**：読むとき、①の `aliasMapFor(取引先)` を Claude への指示文に渡し、読んだあとにも辞書を当てる。辞書で商品が変わった行は「名寄せ辞書で P02（読み取りは P01）」とメモに残す。AI が読んだ元の値は `read` に残す。人が確定したときに辞書へ覚える処理は、受注一覧の確定（`addAlias`、source: line）が持っている
- **CSV の一括登録**：取引先の CSV は⑤の枠（`service.ts` の `customers`）を通る。プレビューでエラーが1件でもあれば保存しない。CSV で直しても LINE のひも付けは消えない。書き出しは `/api/masters/customers?format=csv`
- **デモのリセット**：`resetLineDemo()` は架空のお客さん（`U_demo_…` / `U-demo-…`）の分だけ消し、本物の LINE の人は残す。そのあと、撮影用に `U_demo_kotori` を「ベーカリーカフェ ことり」（C06）にひも付けた状態で入れ直す（リッチメニューの「前回と同じ」がすぐ出るように）
- **撮影の場面の通しテスト**：`line-scene.test.ts` で、3106 と同じ時計（`DEMO_NOW=2026-11-05 11:30`）とデモの人を使い、「前回と同じ → 受付（要確認）→ 受注一覧で確定 → 確定の連絡」を通した。LINE のトークンが入っていても、デモの人には本番の LINE で送らない（fetch を呼ばない）ことも確かめた
- **工程表の設備の制約**：一度④が引き取ったが、③が先に入れ終えていたので③に任せた（④の案は差分にして③へ渡した）

## 3-3. 11/5 昼の作業（締め・自動の確定・スタッフの LINE ログイン・読み取りのやり直し）

- **締めとつなぐ**：③の `checkLeadTime` / `deliveryDayProblem` を LINE に使った。注文フォームでは、納品しない曜日と締めを過ぎた商品は選べない。サーバーでも受けない（画面だけで止めると、古い画面から送られたときに通ってしまう）。LINE受付の画面には、行ごとに締めの理由をそのまま出す（`LeadTimeNote`）
- **代わりの日の提案**：受けられない行は、③の `suggestAlternatives` で代わりの日を探し、確定の連絡に「…には お届けできない商品」と添える。お客さんがそのまま返信したら、読み取りは「前の注文の変更・その日」として読む（提案した内容を、最近の注文の手がかりに入れて Claude に渡す）
- **自動の確定（作者の 11/5 の方針）**：迷わなかった注文だけを自動で確定する。条件は、お店がひも付き済み、全行が辞書か商品名どおり、自信 0.9 以上、印なし、受け付けた時刻で締めと曜日に通る、新しい注文、の全部。だめなときは、そのわけを `autoHold` に残して要確認のまま。AI は値を書きかえない。確定した人は「自動（LINE・迷いなし）」と記録する
- **②の共通部品への置き換え**：「自動で確定」の札と取り消しのボタンは、最初は④の画面に自分で作っていた。FAX・LINE・取り込みで見た目をそろえるため、②の `AutoTag` / `UndoAutoButton` / `isAutoConfirmed` に置き換えた。取り消しの処理も④の分は消して、⑤の `undoAutoConfirm` を使う
- **機能の ON/OFF**：④の設定画面に持っていたスイッチ（LINE の注文・自動の確定・自動の送信・スタッフへの通知）は、①の機能の ON/OFF（`isOn` / `setFlag`）に寄せた。LINE の注文を OFF にすると、トークもフォームも受けない
- **スタッフの「LINE でログイン」**：工場の外（スマホ）から通知のリンクを開いたスタッフが、LINE で本人だと確かめてから画面を見られるようにした
  - スタッフ用の LIFF で LINE の ID トークンをもらい、サーバーで LINE に確かめる（`verifyLiffIdToken`）。登録済みのスタッフで、しかもお客さんにひも付いていない人だけ通す
  - 通したら、署名つき cookie を渡す（HMAC-SHA256。12時間。HttpOnly・Secure・SameSite=Lax）。署名の比べ方は `timingSafeEqual`。秘密が無い・短い（32文字未満）ときは作らない・通さない
  - ログインのあとの行き先は、アプリの中のパスだけ（`//`・`\`・改行・`/api/`・`/liff/staff` 自身は `/` にする）。外のサイトへ飛ばされないように
  - 秘密の値は `scripts/staff-secret.mjs` が `.env.local` に1行足すだけで、画面には出さない
- **外からのアクセスを確かめた**：トンネルを通ったアクセスには `cf-ray` という印が付く。この印を付けた試しの通信で、工場の中からは見られる画面（受注一覧など）が、外からは 403 になることを確かめた。にせの cookie でも 403。外から開けるのは LIFF の入口と Webhook だけ。秘密がまだ無いときは、ログインは「設定されていません」と断る（安全な側）
- **読み取りの「Connection error.」**：⑥の試しで、テストの注文を2件続けて送ると2件とも読み取りに失敗した（50秒あけて1件ずつなら成功）。調べと直しは「4. 試行錯誤」に書いた

## 4. 試行錯誤

- **worktree の node_modules**：本体の node_modules をジャンクションでつないだら、Turbopack が「Next.js が見つからない」で止まった → worktree で `npm ci` し直した
- **「ありがとう」も注文になる？**：注文ではない文章も、品目なしの要確認として残す（AI が勝手に捨てない）。画面には「注文ではないかも」と出す
- **お客さんへの返事**：最初は「ご注文を受け付けました…」と長く書いていたが、「ありがとう」にも同じ返事になるので、決まりどおり「受け付けました（確認中）。」だけにした
- **1作目の注文フォームが「ダサい」**：大きくすることだけを考えて、全部の文字を大きくしていた。調べた結果、今っぽさは「色は1色」「文字の大小の差」「＋が −数＋ に変わる」「下の固定バー」「3段階」で出ると分かった。年配の人向けには「押せる場所を大きく」「前回と同じ」「文字を打たせない」を守った
- **品名が2行に折れる**：＋−を横に置くと「食パン 6枚切」が折れた → ＋−を品名の下の段に移した
- **秘密の値**：ページの文字を読み取る道具は、チャネルシークレットやトークンも一緒に読んでしまう。そのあとは、合いかぎが出る画面では文字の読み取りをやめ、値は作者本人に貼ってもらった。`.env.local` の確認も「何文字入っているか」だけにした
- **シークレットを1行ずれて貼った**：状態の確認（`GET /api/line/webhook` が「入っているかどうか」だけを返す）ですぐ気づけた
- **デモのリセットで本番の注文も消える**：本番の注文を使うテストは、リセットの前に済ませる
- **PC の資源不足（os error 1450）**：開発サーバーを何本も動かすと Turbopack が止まった → 常に動かすのは①の 3100 だけにし、④の確認は vitest でした
- **まっさらなデータベースでのリセット**：`resetLineDemo()` が masters の表より先に動くと「no such table」で止まった → 先に masters を読んで表を作るようにした
- **取り込んだ LINE の記録が消えた**：`line.json` を取り込んだあとでデータベースが作り直され、取り込んだ分が消えた。元のファイルは `line.json.migrated` として残っていたので、①が名前を戻して取り込み直した
- **③の検証で見つかった不具合**：商品を `master.ts` だけで探していたため、③の catalog にだけある商品（ピザ生地玉など）が空になった → `src/lib/catalog.ts` に差し替えた
- **/line がエラーの画面になった**：②の `isAutoConfirmed` は `"use client"` の部品のファイルにあった。それをサーバーの画面（`/line`）から呼んだので、画面ごと落ちた。テスト（vitest）はサーバーとブラウザの区別をしないので通ってしまい、気づけなかった → ①が判定を `src/lib/auto-confirmed.ts`（サーバーでも使える場所）に移して直した。学び：`"use client"` のファイルからは部品だけを使い、判定の関数はサーバーから呼ばない。画面の変更は、テストのほかに実際に開いて確かめる
- **取り消しの制限の提案**：自動の確定を取り消せるのは便利だが、確定の連絡をお客さんに送ったあとで取り消すと、お客さんは「確定した」と思ったままになる。④の画面では、連絡を送ったあとは取り消しのボタンを出さないことにした。⑤の `undoAutoConfirm` でも、連絡を送った注文（`lineNotifiedAt` あり）は断るよう提案した（画面のボタンを隠すだけだと、ほかの入口から取り消せてしまう）
- **秘密を作るコマンドがこわれた**：最初は秘密を作って `.env.local` に足す1行のコマンドを手順書に書いたが、記号がシェルに解釈されて動かなかった → `scripts/staff-secret.mjs` にして、試しのファイルで確かめてから手順書に書いた。値は画面に出さない
- **ログインの画面のちらつき**：ログインを「画面が出たら（effect の中で）」始めると、lint に「effect の中で状態を変えている」と止められた → LINE の部品（SDK）を読み終えたとき（Script の onLoad）に始めるようにした
- **Connection error. の調べ**：
  - まず疑ったのは「Claude に同時に頼むと断られる」こと。④の場所で、本物の Claude に3件同時に頼んだ → 3件とも成功
  - 次に、⑥と同じ形（開発サーバーの Webhook に、2件を同時に送る）を④の場所で試した。デモの状態（LINE の合いかぎなし）で、本物の LINE には何も送らない → 2件とも読み取れた
  - なので、同時に送ること自体が原因ではなさそう。いちばんありそうなのは、その数秒〜数十秒だけ通信が切れたこと。Claude の SDK も自分でやり直すが、間は 0.5〜8秒で2回だけなので、少し長い途切れでは3回とも失敗する
  - 直し方：一時的な失敗（通信の途切れ・時間切れ・混み合い 429/529・サーバーの 5xx）だけ、5秒→20秒→45秒と間をあけて、最初のほかに3回までやり直す。断られた・頼み方がちがう（400）ものは、やり直しても同じなのですぐあきらめる。同時に頼むのは2件までにして、3件目は待たせる（一度に押し寄せないように）。1回の待ちは2分まで（SDK の初期値は10分で、長すぎる）
  - それでもだめなら、今までどおり元の文章つきの「要確認」で残す（注文は消えない）。失敗の説明には、下の原因（例「Connection error.（ECONNRESET）」）とやった回数を添える。前は「Connection error.」としか残らず、原因を追えなかった
  - テストでは、待ち時間を 0 にして、「2件同時で最初は切れても読み取れる」「4回でだめなら要確認で残る」を確かめた
  - ついでに分かったこと：試しの開発サーバー（Turbopack）を動かしたまま全部のテストを流すと、「ファイルが見つからない」で2件落ちた。サーバーを止めたら全部通った

## 5. Claude Code で使った機能

- **git worktree の並行セッション**：④専用のブランチで作業し、マージは進行役に任せた。ほかのセッションとはメッセージで連絡（型の変更・proxy の変更・マージの依頼）
- **Claude in Chrome**：LINE の設定画面を開く・入力欄を埋める・「公開」の確認画面まで進める。ログイン・アカウント作成・規約への同意・合いかぎの貼り付けは作者本人
- **Claude のブラウザ（アプリ内）**：注文フォームをスマホの幅で開いて、押して確かめた（＋−、テンキー、確認シート、受付、履歴）
- **サブエージェント**：ほかの LINE 注文の画面の調べものを任せ、その間に自社の HP の色を調べた
- **ヘッドレス Chrome**：リッチメニューの画像（HTML → PNG）
- **vitest**：③が書いた `line.test.ts` で、読み取り → 注文、変更、確定の連絡を確かめた

使っていない機能：Claude API の tool use（読み取りは構造化出力だけで足りた）、画像の読み取り（LINE の写真の注文は今は「文章かフォームで」と返すだけ）、push・デプロイ（進行役と作者の判断）

## 6. 守ったルール

- AI がやるのは「読み取り」と「要確認の印」まで。直すのは人。読み取りの元の値（read）と人の修正（edits）は残す
- お客さんへの自動の返事は「受け付けました（確認中）。」だけ。確定の連絡は、人がボタンを押したときだけ、1回だけ
- ログイン・アカウント作成・規約への同意・パスワード・合いかぎの貼り付けは作者本人。元に戻せない操作（チャネルの公開）は、作者の OK を取ってから
- 秘密の値（チャネルシークレット・トークン）は git に入れない（`.env.local`）。このメモにも書かない
- 公開リポジトリなので、注文フォーム・リッチメニューに自社のロゴ・社名・写真を入れない（色だけ参考にした）。テストのお客さんは架空（`U_demo_…`）
- 本番の LINE で、作者以外には何も送らない
