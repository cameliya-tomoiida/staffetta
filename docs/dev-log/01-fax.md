# ① FAX の入口 — 作業記録

担当: FAX 読み取り・元のFAXと並べる確認画面・共通の型・Gmail からの自動取り込み
期間: 2026-11-04（ハッカソン期間中に新しく作成）

---

## 1. 何を作ったか（流れ）

```
複合機 ─PDF→ Gmail（ラベル「FAX受信」）─GAS 1分おき→ POST /api/fax/inbound
   → 受信箱（通知音・バナー）→ Claude が読み取り（種類・送り主・向き・明細）
   → 確認画面（左: 元のFAX / 右: 読み取り結果）→ スタッフがタップで直して確定
   → 共通の Order 型に入り、集計・製造計画・発注（②③）へ
```

| 順番 | やったこと |
|---|---|
| 1 | 注文の共通の型 `src/data/types.ts` を最初に決めて、並行で動く4つのセッションの土台にした（FAX・LINE・インフォマート・専用サイト・メール・スプレッドシート・電話を同じ形に） |
| 2 | 架空の取引先・商品・材料のマスターと、架空のFAX注文書（8枚）を作った。実在の取引先は使わず、形だけ実際の運用（週間表・入数指定の袋・丸で選ぶ欄・横向き・逆さま）にそろえた |
| 3 | Claude で FAX の PDF を読み取る処理 `src/lib/fax-reader.ts` |
| 4 | 確認画面: 元のFAXと並べ、行を選ぶとFAX上の同じ行が光る。数量はテンキー、商品は選ぶだけ。誰が何を何から何に直したかを記録 |
| 5 | FAX の種類分け: 注文 / 変更・訂正 / 仮発注 / 仕入先の返信 / 広告 |
| 6 | 変更FAX は元の注文を探して差分で見せ、確定するまで元の注文は書き換えない |
| 7 | 仮発注 → 本発注で自動置き換え（古い方は取り消し・リンクを残す） |
| 8 | 初めての取引先の様式は Claude が下書き → 人が承認するまで受注に入れない |
| 9 | Gmail → GAS → ハブの受け口。届いたらすぐ読み取りを始め、受信箱は自動更新・通知音 |
| 10 | トンネル経由の外部アクセスは受け口だけ通す（`src/proxy.ts`） |

## 2. Claude API の使い方

- モデル: `claude-opus-5-5`（adaptive thinking、effort: high）
- 入力: FAX の PDF をそのまま `document`（base64）で渡す。画像に変換しない
- 出力: **Structured Outputs**（Zod スキーマ → `betaZodOutputFormat`）。`client.beta.messages.parse()` で型付きの結果を受け取る
- 安全: 断られたとき用に server-side fallback（`fallbacks: "default"`）を付け、`stop_reason: "refusal"` は「手入力で」と画面に出す
- 速さ: 未読をまとめて並行で読む（8枚で約1分）

### 指示（システムプロンプト）の工夫
- **AIの役割を「書いてあるとおりに読む」「人が確認すべき所に印を付ける」までに限定**。袋→個の換算はさせず、`quantity`（書いてある数）と `pieces_per_unit`（入数）を分けて返させ、換算はプログラムで行う（同じ入力なら同じ結果になるように）
- 訂正の跡（二重線）は「書き直した後の数」を読み、`attention` に「訂正あり 20→25」と書かせる
- 丸で選ぶ欄（白・黒）は選ばれた方を品名に含めて、`attention` にも書かせる
- 空欄の行は注文なし（定番表が多いため）
- 得意先一覧・仕入先一覧・商品一覧・**スタッフが過去に承認した品名の対応**をプロンプトに入れ、承認済みの対応を優先させる（使うほど正確になる）
- 仕入先一覧を入れたことで、仕入先からの注文請書を「注文」と取り違えなくなった

### 自信度の出し方
- 1行ごとに `confidence`（0〜1）と `attention`（理由の文章）を返させる
- 画面では「`attention` がある」「`confidence` < 0.8」「商品が決まっていない」のどれかで黄色にする
- 1行ごとに `y_percent`（正しい向きにしたページ上の縦位置）も返させ、確認画面で元のFAXの同じ行に帯を出す

### 結果（架空FAX 8枚）
- 数量はすべて正しく読めた（訂正 20→25、3個入×11袋、変更前45→変更後50、仮発注 80→本発注 92 など）
- 種類（注文・変更・仮発注・仕入先の返信・広告）、送り主、向き（逆さま2枚）もすべて正しく判定

## 3. 試行錯誤して直したこと

| 起きたこと | 原因 | 直し方 |
|---|---|---|
| 最初の読み取りで全行が「要確認」 | 架空FAXを「FAXっぽく」加工したとき、縮小＋ぼかし＋2値化で印刷の文字を潰しすぎた（手書きの数字は読めていた） | 本物のFAX程度の解像度・ノイズに弱めた。品名も読めるようになり要確認は本当に怪しい行だけに |
| 受信箱のFAXの絵が出ない | Python で作ったPDFの白黒1ビット画像を pdf.js がうまく描けなかった／プレビューが裏に隠れていて描画が止まっていた | PDFをグレースケール画像で保存し直し、ワーカーを明示して作る |
| 逆さまのFAX | 実際に33通中15通が逆さま・横向き | Claude に `rotation_degrees` を返させ、表示はその角度で回す。人が回転ボタンで直せる |
| 変更FAXで元の注文が書き換わってしまう設計の危うさ | 確定前に元を直すと、読み間違いが本番に入る | 変更FAXは `intent: "change"` の別の注文として入れ、人が確定した時だけ元の行を直して記録を残す。集計は `intent: "new"` だけ数える（③と取り決め） |
| 仮発注と本発注の二重計上 | 同じ取引先・納品日に2つの注文 | 本発注を確定すると、仮発注を取り消して `supersededBy` / `supersedes` でつなぐ |
| 新しい様式の特徴に「逆さまで受信」と書かれる | その1枚だけの事情まで様式に入れていた | 指示に「向き・かすれ・受信日時は書かない」を足した |
| 画面全体が 500 エラー（Next.js 16 の cacheComponents） | 動的なデータを Suspense の外で読んでいた | デモでは cacheComponents を外し、読み込みは `connection()` で毎回 |
| マージ途中の package.json が壊れたまま残る | 並行セッションのマージ中の状態を Turbopack がキャッシュ | `.next` を消して再起動 |
| 画面全体が 500 エラー（Tailwind） | 並行開発の worktree（`.claude/worktrees/`）がリポジトリの中にあり、Tailwind v4 がその `node_modules` まで読みに行っていた | `globals.css` に `@source not "../../.claude";` |
| トンネルで社内の画面まで外から見える心配 | クイックトンネルは全部の道を外に出す | `src/proxy.ts` で、Cloudflare 経由は受け口（FAX・LINE）だけ通し、受信箱・確認画面・ボタンは 403 |
| 白黒2値（CCITT）のFAXが確認画面で真っ白 | pdf.js v6 は CCITT の画像を wasm で読み解く。`wasmUrl` を渡していなかったので「JBig2 failed to initialize」→「Dependent image isn't ready yet」で何も描かれなかった（Chrome 標準ビューアでは正しく出るので PDF は正常） | `pdfjs-dist/wasm/` を `public/pdfjs-wasm/` に置き、`getDocument({ wasmUrl: "/pdfjs-wasm/" })`。あわせて描画の取り消し（React の二重実行で描画が重ならないように） |

### 本物の経路での確認（11/4 夜）
- 担当者の許可をもらい、架空の注文書PDFを添付したメールを fax-inbox に送り、「FAX受信」ラベルを付けた（迷惑メールに入っていたので「迷惑メールではない」に）
- 約1分で Gmail → GAS（1分おき）→ トンネル → `/api/fax/inbound` → 受信箱 → Claude の読み取り まで届いた。送り主・180°回転・数量（3個入×11袋、2個入×39袋）とも正しかった
- このとき白黒2値のPDFが真っ白になる不具合が見つかり、上のとおり直した。本物の複合機のFAXも白黒2値で来る可能性が高いので、撮影前に見つかってよかった

### 撮影日の時計（DEMO_NOW）での確認
- 物語の日付は 2026-11-05（木）11:30。`.env.local` に `DEMO_NOW` と `NEXT_PUBLIC_DEMO_NOW` を入れて起動すると、共通の時計（`src/lib/clock.ts` の `nowIso()` / `nowMs()`）がその時刻から進む
- ①では、確定・修正・受信の時刻をすべてこの時計から取るように変えた。テスト送信（`npm run fax:simulate`）の受信時刻も時計にそろえる（本物の Gmail はメールの日時のまま）
- 実際に起動してテスト送信し、受信箱に「Gmail経由・11/5 11:30 受信」と出ること、保存された受信時刻が 2026-11-05T02:30Z（日本時間 11:30）であることを確かめた。確認後は2行を外して元に戻した

### 11/5 の実用化で、落ちて・気づいて・直したこと

**読み取りの精度を数で測った（docs/fax-accuracy.md）**
- 架空の FAX 11 枚・39 行を、正解と1行ずつ比べた。行はすべて合っていた。ところが、正しい行の 67% に「念のため見る」の黄色が付いていた。
- 原因は2つ。指示文に「1と7、0と6に注意する」と書いたら、それが全部の行の注意の文に写っていた。もう1つは、使用日・仮発注の説明のような「確認が要らない説明」まで注意の文に書いていたこと。
- 「注意の文は、人が FAX を見て確かめないと危ない行だけ。説明はメモへ」と、書くもの・書かないものを例つきで指示文に書いた。黄色は 26→4 行（訂正・丸の選択・バラ指定だけ）に減った。行は直す前も後も 39/39 のまま。
- 本物の FAX（逆さま・2枚つづりの変更の連絡票）でも、字の読み取りは全部合っていた。外れたのは「自社のどの商品か」だけ（マスタが架空なので決められないのが当たり前）で、そこにはちゃんと印が付いていた。
- 読み直すと自信度が 0.5→0.6 になり、赤枠が黄に変わることも見つけた。「得意先一覧に無い送り主の行は必ず赤枠」を足した。

**自動確定（担当者の方針「迷った所だけ人が見る」）**
- 判定は純関数（src/lib/fax-auto.ts）。AI は値を書き換えず、「読み取りのまま確定してよいか」だけを決める。
- 変更の FAX が元の注文より先に届くと、元の注文が見つからない。元の注文が確定したときに、待っている変更の FAX を見直すようにした（テストで「変更が先」を再現してから直した）。
- 変更 FAX の確定の前に、元の注文が別の FAX でまだ確認待ちなら止めるようにした。気づいたきっかけは、通しの確認で「元の注文なし → 追加として入れる」と出たこと。そのまま押すと、あとで元の FAX を確定したとき数が二重になる。

**画面が 20 秒かかった**
- 確定ボタンが 21 秒、どの画面も 3〜20 秒かかった。測ると、上の帯の数（/api/today）1回に 35 秒かかっていた。
- まず結果を 30 秒ためる形にした。そのあと③が、原因は計算ではなく、開発サーバー（Turbopack）が作業フォルダの中の worktree（5つ・node_modules 込み）を見張っていたことだと突き止めた。
- 3100 を本番モード（build → start）に切り替えると、0.05〜0.5 秒になった。
- 長く使ったとき（3年分）の確定の時間も 1.2 秒→0.55 秒に縮めた。全件の写し（structuredClone）を作るのをやめ、読んだときの JSON の文字列と比べる形にした。

**/line がエラーの画面になった（server から client の関数を呼んだ）**
- 入れ替えのあと、全ページを開いて確かめたら /line だけ digest 付きのエラーだった。
- サーバーのログでは「isAutoConfirmed は client にあるのでサーバーから呼べない」。"use client" の部品のファイルにある普通の関数を、サーバーの画面から呼んでいた。
- tsc もテストも通るので、ページを開くまで分からない種類の不具合。判定を普通のモジュール（src/lib/auto-confirmed.ts）に移して直した。
- それからは「入れ替えたら左メニューの全ページを開き、200 だけでなく中身の文字とエラー表示が無いことまで見る」を毎回行っている。
- ほかに同じ形が無いかも、src 全体を機械的に調べた。

**FAX の2枚並び**
- 「スクロールせずに2枚並べて」の指示どおり横に並べた。ところが本物の FAX はページが横長で、半分の幅では小さすぎた（管理役が実際の画面で見つけた）。
- 描いたページの縦横から判断し、横長なら縦に積む（1枚を横いっぱい）ようにした。

**トンネル経由のログイン（proxy）**
- 通す・止めるの判断を純関数（src/lib/tunnel-access.ts）にして、先にテストで決まりを固めた。④の cookie の確かめ方（署名と期限）は、master に入ってからつないだ。
- 「ログインしていれば全部」でも、全データの書き出し・取り込み（/api/backup・/settings/backup）は LAN だけにした（画面の「戻す」ボタンも全データを入れ替えるので、API だけでは足りなかった）。

**マージ中の作業フォルダ**
- 管理役のマージの途中に、気づかず①のファイルを git add してしまった。すぐに①の3つだけ git reset で外し、管理役に知らせた。管理役はマージを取り消して①のコミットを先にした。
- それからは、コミットの前に .git/MERGE_HEAD が無いかを見ている。

**アラートの時刻と設定のスイッチ**
- 記録の時刻が UTC のままで、画面で9時間ずれていた（②が見つけた）。記録は日本時間（+09:00）にそろえ、「あとで」「期限」の比べ方を文字ではなく時刻での比較にした（形が混ざっても正しく比べられる）。
- FAX の自動確定のスイッチが、自前の設定と機能の一覧の2か所にあった。機能の一覧（features）だけに一本化した。

**5分ごとの判定を本番で動かす前に止めたもの**
- ⑤の時刻で動く仕事は、⑤の設定の既定がすべて ON（発注書の自動承認など）だった。そのまま5分ごとに回すと、本番の DB で自動承認が動く。
- 機能の一覧で自動のどれかが ON のときだけ呼ぶ形にして、既定は全部 OFF にしてから本番に入れた。

## 5. 守ったルール
- AIは読み取りと印付けまで。値を直すのは人。人が確定・修正した値をAIが上書きしない
- 元の読み取り値（`read`）と修正の記録（`edits`：誰が・いつ・何を・何から何へ）を必ず残す
- 公開リポジトリなので、取引先・レシピ・単価はすべて架空。秘密の値（APIキー・合言葉）は `.env.local` だけに置き、表示もしない
