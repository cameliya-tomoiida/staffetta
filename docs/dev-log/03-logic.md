# ③ 内部ロジック（集計・入数換算・発注書・製造計画・材料・原価）— 作業記録

担当: `src/lib/` の計算（純関数）とテスト、架空の製造マスター、デモ用の注文・初期化、検証役（他の担当の取り込みのテスト・通し確認）
期間: 2026-11-04〜（ハッカソン期間中に新しく作成）

---

## 1. 何を作ったか（流れ）

```
確定した注文（どの入口でも同じ Order）
  → 集計（納品日×商品、個・P・袋・ケースを個数にそろえる。変更・取消・仮発注は数えない／仮は別枠）
  → 入数換算（65個 → 6個入×11袋・余り1、食パン 3斤=30枚 → 1枚入・2枚入）
  → 仕入品の発注書の下書き（仕入先×便。前日入れの品は前日の分へ）
  → 製造計画（生地kg＝分割g×個数÷(1−ロス率)、ベーカーズ％で材料kg、ミキサー回数、ラインの上限の警告）
  → 工程表（パンは納品時刻から逆算、ピザは前日仕込み＋当日朝から）
  → 材料の所要量 → 何日先まで見て、在庫・リードタイム・最小ロットから材料の発注書の下書き
  → 原価・粗利（材料費はロス込み、仕入品は実際に買う袋数で）
```

`runPipeline(orders, date)` を1回呼ぶと、画面（/plan・/purchase）に要るものが全部そろう。関数の一覧と式は [src/lib/README.md](../../src/lib/README.md)。

| 順番 | やったこと |
|---|---|
| 1 | 業務の資料（商品リスト・レシピ・原価表の Excel）を **読むだけ** で開き、工程・発酵時間・分割g・ロス率・ベーカーズ％の「形」を学んだ。数字はすべて丸めたり変えたりした架空の製造マスター `src/data/production.ts` を作った（実在のレシピ・単価・取引先は入れていない） |
| 2 | 集計（`aggregate.ts`）と単位（`units.ts`）。人が確定した値（`pieces = quantity × piecesPerUnit`）を使い、保存値と食い違えば注意を出す |
| 3 | 入数換算（`packing.ts`）と仕入品の発注書（`purchase.ts`）。得意先ごとに袋を分けるか、まとめて割るかを選べる |
| 4 | 製造計画・工程表（`production.ts`）、材料（`materials.ts`）、通し計算（`pipeline.ts`）、原価（`cost.ts`） |
| 5 | 共通の型の変更（`intent`・仮発注）に合わせて、集計の決まりを直した |
| 6 | 発注書の保存（`purchase-store.ts`／決まりは純関数 `purchase-records.ts`）。下書き→承認（人と時刻）→送信済みの順しか進まない |
| 7 | 商品ごとのリードタイム判定（`leadtime.ts`）、棚卸からロス率の補正案（`stocktake.ts`）、材料を何日先まで見る（`material-plan.ts`）、前日入れ |
| 8 | リポジトリの README、デモの初期化 `npm run demo:reset`、デモ用の注文（あした 11/6 分と来週の定期分） |
| 9 | 検証役: ④⑤の取り込みのテスト、`npm run check`、デモの流れを自分でサーバーを立てて通した |
| 10 | 共通の時計 `clock.ts`（デモの「今日」をそろえる）と、材料を「今から頼んで間に合う日」から計画する形 |

## 2. 関数設計の考え方

- **計算に AI を使わない。** 集計・換算・計画・原価はふつうのプログラム（純関数）。同じ入力なら必ず同じ結果になり、テストで確かめられる。AI（Claude）は入口の「読み取り」と「要確認の印」だけ（①④⑤の担当）。
- **入力は共通の `Order` だけ。** 入口（FAX・LINE・メール…）を計算は気にしない。だから入口が増えても計算は変えなくてよい。
- **マスターを2つに分けて、片方からだけ引く。** ①の `master.ts` は直さず、足りない項目（生地・工程・入数・便・ピザ）は③の `production.ts` に足した。画面も計算も `catalog.ts` の `findProduct` などから引けば両方が見える。
- **人の判断を上書きしない。** 発注書は必ず `draft`。承認済み・送信済みは計算し直しても上書きしない。ロス率の補正は「案」として返すだけで、人が承認したものだけを `lossRates` で渡す。
- **全社一律の締めを作らない。** 締めは商品のリードタイムと、仕入先の便の締めから出す。
- **画面が1回呼べばよい形。** `runPipeline` の戻り値に、集計・発注書・製造計画・工程表・材料・警告をまとめた。原価は `dayCostSummary(r)`。
- **困ったら警告で止めずに続ける。** 単位が分からない・商品が空・上限超え・締め超えなどは `warnings` に出して計算は続ける（現場で人が判断する）。

## 3. テスト

- vitest。`npm test`、合否判定は `npm run check`（`next typegen` ＋ `tsc --noEmit` ＋ `eslint` ＋ `vitest run`）。
- ③の計算のテスト: 必ず入れると決めたもの（病院65個 → 6個入×11袋・余り1、単位の混在、ロス率）に加え、集計の決まり（変更・取消・仮発注）、入数の候補選び、便ごとの発注書、締め、工程の重なり・すき間なし、材料・最小ロット・締め超え、原価、棚卸の補正案、前日入れ、デモの初期化、時計。
- 検証役のテスト（`src/lib/channels/__tests__/`）: ⑤の取り込み（インフォマート・取引先サイトの CSV・スプレッドシート・メール）と④の LINE を、各担当が置いた架空サンプルで通し、`rules.ts` で「共通の決まり」（要確認・intent・元資料への参照・pieces・read を残す・理由の印）に合うかを確かめる。
  - AI の読み取りはテストでは呼ばず、「Claude が返すはずの形」の見本をスキーマで検査してから差し込む（毎回同じ結果・費用ゼロ）。
  - 保存先はメモリ（`memdb.ts`）に差し替え、本物の `data/` には書かない。
  - 見つけた不具合は `it.fails` で記録して担当に伝え、直ったら `it` に戻す（直ったことがテストで分かる）。
- テストの「今」は `DEMO_NOW` で固定（日によって結果が変わらない）。

## 4. 試行錯誤して直したこと

- **工程表を後ろから組むと、発酵が延びた。** 設備（ミキサー・オーブン）の空きに合わせて工程ごとにずらすと、ミキシングと1次発酵の間にすき間ができ、生地が待たされる。→ 生地の工程をひと続きの塊として並べ、設備がふさがっていれば塊ごと前にずらす形にした。
- **パンが前日の夜中に始まり、毎回「間に合わない」と赤く出た。** 夜班があるので、ラインに「いちばん早く始められる時刻」（パンは前日21:00）を持たせ、それより前だけ注意にした。
- **材料の発注書が全部「締めを過ぎています」になった。** デモの今日（11/5）では、あした 11/6 の材料はもう頼めない。→ 「今から頼んで間に合う日から計画し、間に合わない日の不足は『電話で確認してください』の警告だけ」にした（進行役が決定）。あわせて、来週の確定済みの注文をデモに足し、材料の3つの頼み方（受発注サイト・取引先のサイト・FAX）が見えるようにした。
- **デモの「今日」が画面と LINE でずれた。** 本物の時計を使うと、撮影日によって「明日」が変わる。→ 共通の時計 `clock.ts`（`DEMO_NOW` から始まって本物と同じ速さで進む。止めると受け取った順が崩れるため）を作り、各担当に差し替えを頼んだ。
- **前日に仕入れる品の持ち方で、⑤と行き違いがあった。** 最初は「注文を分けて `purchaseDaysBefore` を持たせる」と伝えたが、⑤は行のメモに書く形で先に作っていた。→ ③の側で、行の品名から⑤のコード表（前日の振り分け）を引く `lineDaysBefore` を作り、⑤は元の形のままでよいことにした（分ける形にも対応）。
- **テストの見込み違い。** 「20個を 6個入・8個入で」は余りがどちらも4で、袋の少ない8個入が正しかった。期待値を手で計算し直してから直した（コードではなくテストが間違っていた）。
- **取り込みが新しい商品を空にしていた。** 検証のテストで、ピザの 27cm などが④⑤の取り込みで理由なしに空になるのが分かった。→ 担当に伝えて `catalog.ts` から引くように直してもらった。
- **型チェックが画面の型で落ちた。** Next.js の生成型（`PageProps` など）が無いと `tsc` が落ちる。→ `npm run check` の先頭で `next typegen` を走らせた。`server-only` はテストでは中身のない部品に差し替えた。

## 5. Claude Code で使った機能・使っていない機能

### 使ったもの
- **git worktree**: 専用の worktree・ブランチで作業。区切りごとにコミットし、`git merge master` で他の担当の変更を取り込んだ（push・マージは進行役）。⑤のブランチとの組み合わせは、試しにマージしてテストを流し、すぐ取り消して確かめた。
- **セッション間のメッセージ（SendMessage）・セッション一覧**: 進行役から仕事を受けて報告し、⑤とは直接やりとりして前日便の持ち方を合わせた。
- **ファイルの読み書き・検索、シェル（Bash）**: Excel の資料は Python（openpyxl、読み取り専用）で開いた。vitest・tsc・eslint を区切りごとに実行。TypeScript のスクリプトは tsx で動かした（デモの初期化）。
- **アプリ内のブラウザ（Browser pane）**: 開発サーバーを立て、デモの流れ（初期化 → FAX 受信・読み取り・確定 → 変更の反映 → 製造計画 → 発注書の承認 → LINE 注文 → ひも付け → 確定 → 確定の連絡）を自分で通した。LINE は設定を空にしたデモモードで動かし、本物には送っていない。
- **タスクリスト**: 作業の順番を画面に出して進めた。

### 使っていないもの
- サブエージェント（Agent ツール）・ワークフロー: 使っていない（このセッション1つで作業）。
- Plan モード・hooks・スキル: 使っていない。
- Claude API: ③の計算では使っていない（設計の決まり）。デモの通し確認で、①の FAX 読み取りを1枚だけ動かした。
- ユーザーの Chrome（Claude in Chrome）: 使っていない。

## 6. 守ったルール

- **AI は読み取りと印付けまで、値を直すのは人**: 計算は人が確定した注文だけを数える。人が直した値を計算が上書きすることはない。
- **元の値と修正履歴を残す**: デモの注文にも、人が直した跡（`edits`）を入れた。
- **発注は 下書き → 人が承認 → 送信**: 計算が作るのは下書きだけ。承認には人の名前が要り、承認した時刻を記録する。承認前は送信済みにできない。
- **マスターを勝手に書き換えない**: ロス率は補正「案」を返すだけ。
- **公開リポジトリ**: データ（取引先・商品・単価・レシピ）はすべて架空。資料の Excel は読むだけで変えず、数字は丸めたり変えたりした。この記録・コード・テストにも実在の社名・個人名は書いていない。
- **他の担当のファイル**: 共通の型（`types.ts`）・①の `master.ts`・`store.ts`・④⑤の取り込みのコードは直さず、直してほしい点は進行役か担当に伝えた。
- **パスワード・ID・送信**: パスワードや ID は入力していない。本物の LINE・FAX・仕入先には何も送っていない。
