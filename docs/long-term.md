# 長く使ったとき（1か月・1年・3年）、データはどうたまるか

担当者の最初の指摘「1か月・1年・3年と使ったら、どうたまっていくのか」に答えるための試験の記録です（2026-11-05、③）。

## 試験のしかた

架空の取引先13社が、営業日（日曜・年末年始は休み）に、いつもの商品を数行ずつ注文する、という1年分・3年分のデータを作って、画面と同じ処理の時間を測りました。

- 入口は FAX・LINE・メール・取引先のサイト・電話・ドライバーをまぜています（取引先マスタの「主な入口」のとおり）。
- 変更の連絡（5%）、取り消し（2%）、仮発注 → 本発注（3%）もまぜています。
- 発注書は、毎日の計算どおりの下書きを作り、過去の分は「送信済み」にしています。
- 材料・包材の在庫は、毎週の棚卸で入れ直しています（マスタの変更の記録がたまります）。
- 本物の `data/hub.sqlite` には書きません。試験用の DB ファイル（`data/sim/`）に作ります。

```bash
HUB_DB_PATH=data/sim/year.sqlite npm run simulate:year
HUB_DB_PATH=data/sim/year.sqlite npm run measure:db
HUB_DB_PATH=data/sim/3y.sqlite npm run simulate:year -- --years 3
HUB_DB_PATH=data/sim/3y.sqlite npm run measure:db
```

時間は、開発用のパソコン（Windows・Node 24）で3回測った中のいちばん短い値です。

## 結果

| | 1年 | 3年（直す前） | 3年（直したあと） |
|---|---|---|---|
| 注文 | 3,646件 | 10,929件 | |
| 受信した FAX | 1,038件 | 3,114件 | |
| 発注書 | 2,040件 | 6,106件 | |
| DB ファイルの大きさ | 11MB | 33MB | |
| 画面を開くときに読む | 0.16秒（全部） | 0.33〜0.42秒（全部） | **0.04秒**（最近60日＋要確認など。注文 605件） |
| 受注一覧の検索（今月・取引先・状態） | 0.11〜0.16秒 | 0.36〜0.45秒 | **0.001〜0.008秒** |
| 受注一覧の検索（文字・すべての期間） | 0.13秒 | 0.46秒 | **0.06秒** |
| 製造計画（/plan） | 0.11秒 | 0.41〜0.46秒 | **0.04秒** |
| 計算だけ（製造計画・発注書・材料） | 0.004秒 | 0.012秒 | 0.013秒 |
| 注文を1件確定する | 0.4秒 | 1.0〜1.2秒 | （撮影のあとに①が直す） |
| バックアップの書き出し（PDF なし） | 0.07秒・11MB | 0.2〜1.8秒・31MB | |

このほかに、受信した FAX の PDF がファイルでたまります（`data/fax-inbox/`、DB の外）。1枚 約150KB として、**1年で約150MB**の見込みです。

## わかったこと

- **データの量**：1年で約11MB・注文 3,600件ほどです。SQLite は数GB まで扱えるので、量としては10年以上たまっても問題ありません。
- **計算（③）**：注文が増えても、その日の計算は 0.01秒ほどで変わりません。
- **遅くなる所**：今の保存の口は、画面を開くたび・1件書くたびに「全部の行」を読みます。1年なら気になりませんが、3年で1件の確定が1秒、検索が0.4秒ほどになります。
  - 検索の SQL 自体は、日付・取引先・状態に索引があるので、3年でも 0.04秒ほどです。遅いのは、検索の前に全部を読んでいるところです。
- **FAX の PDF**：DB よりも PDF のほうが大きくなります。バックアップに PDF を入れると、1年で 200MB 前後の1ファイルになります。

## このままの作りで、どこまで使えるか

- **1〜2年**：今の作りのままで、ふだん使いに困らない速さです。
- **3年以上**：画面と検索は、もう何年たまっても速さが変わりません（最近の分と索引だけを使うため）。残る「1件確定に1秒」も、①の「1件だけ書く口」が入れば、0.05秒ほどになる見込みです。

### 直した所・これから直す所

1. **直した**：検索の前に全部を読むのをやめた（`ensureStore()`：表の準備と移行だけ）。
2. **直した**：画面を開くときは「最近の分」だけ読む（`readRecentDb()` / `loadRecentDb()`）。
   - 注文は「納品日が60日前より後」＋「要確認・仮発注は全部」、FAX は「60日以内」＋「まだ確定していないもの」、発注書は「60日以内」＋「まだ送っていないもの」。
   - 古いものは検索（索引あり）で見る。
   - これは読むだけ。書き込み（`updateDb`）は今までどおり全件を読む。最近の分だけのデータを書き込みに渡すとエラーにして、読まなかった古い行を消さないようにした。
3. **一部直した（11/5）**：書き込み（`updateDb`）は全件の写しを作らず、読んだときの文字列と比べる形にした（3年で1件の確定 1.2秒 → 0.55秒）。**撮影のあとに①が直す**：1件を書くときは、その1件だけを書く口を使う（確定の処理で元の注文・仮発注を探す所を書き換えるので、撮影の前は見送った）。
4. **直した（11/5）**：バックアップの既定を「PDF なし」にした（`/api/backup?files=1` で PDF も、`&month=2026-11` でその月の分だけ）。
5. **ハッカソンのあとに一度にそろえる**：2列キーのマスタ（便など）で、json の `id` が行の鍵（例「S07|1」）で上書きされる（③の `toStoredRows`・⑤の CSV 取り込みが `id = rowId(...)` を入れているため）。直すなら、①の保存の口に行の鍵を `id` とは別に渡せる形（例 `_key`）を足し、③⑤の書く側と、②③④⑤の読む側・「直す・使わない・戻す」を同時にそろえる。いまは③が読む側でそろえているので、撮影と提出が終わるまでは今のまま。

## 古いデータの扱い（案）

- **一覧の既定**：受注一覧・FAX 受信箱・発注書の一覧は、**13か月より前を既定の表示から外します**（検索で「すべての期間」を選べば出る）。前の年の同じ月と比べられるように、13か月残します。
- **書き出して別に置く**：年に1回、前の年の分を「バックアップの書き出し」で1つのファイルにして、別の場所（NAS・外付けディスク・クラウドのフォルダ）に置きます。
- **消す**：DB から消すのは、書き出しを確かめたあとに、人が決めたときだけにします（自動では消しません）。量としては残しておいても困りません。
- **FAX の PDF**：月ごとのフォルダに分けて、1年より前のものは別の場所へ移せるようにするのがよいです。バックアップは「データだけ（毎日）」と「PDF も（月に1回）」に分けると、毎日のバックアップが軽くなります。
- **記録は消さない**：AI が読んだ元の値（read）と人の修正（edits）、マスタの変更の記録（master_history）は、あとで確かめられるように残します。量は少ない（マスタの記録は1年で数MB）です。
